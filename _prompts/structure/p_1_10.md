# Prompt 1.10 — Normalization Layer (B3 RAW → Normalized) — **suno-wallets**

Implemente a **camada de normalização** que transforma o **RAW data** (persistido no 1.9) em **tabelas normalizadas** para **transações** e **posições**, sem aplicar regras de negócio de consolidação (sem cálculos de preço médio, rentabilidade etc.). O foco aqui é **extrair/flatten** com **tipagem adequada**, **idempotência**, **linhagem** e **observabilidade**.

## 🎯 Objetivos
- Ler **RAW data** das tabelas do 1.9 e **normalizar** em estruturas **relacionais**.
- Manter **linhagem** completa (FK para o RAW, sequência dentro do payload, hash determinístico).
- Garantir **idempotência** (não duplicar). Suportar `force` e `dryRun`.
- Preparar base para a Fase 2 (consolidação/cálculos).

- `gross_value` (numeric(28,10), null)
- `currency` (varchar(8), null) — ex.: `BRL`
- `extra_json` (jsonb, null) — campos não mapeados do payload

**Observações de projeto:**
- **Linhagem**: manter `raw_id` + `sequence_in_raw`. Nunca perca referência ao RAW.
- **Idempotência**: Upsert com base no `normalized_hash` + chaves de contexto.
- **Precisão**: usar `numeric(28,10)` para quantidades/valores; evite `float`.

## 🔎 Regras de Normalização
- **Sem tratamento de negócio**: **não** calcular preço médio, P&L, impostos etc.
- Converter datas para **DATE** (`YYYY-MM-DD`) quando forem datas de referência/negociação.
- Normalizar `side` para valores mínimos (`BUY`/`SELL`/`OTHER`). Valores desconhecidos → `OTHER` e registrar em `extra_json`.
- `ticker` deve ser **upper-case**, `cpf` somente dígitos (11).
- **Mascarar CPF** em logs; **nunca** logar tokens.
- Se um campo não existir no payload, manter `NULL` ou registrar no `extra_json`, **sem inventar valores**.

## ⚙️ Endpoint & Fluxo
### `POST /b3/normalize/run`
**Body (JSON):**
```json
{
  "cpf": "00000000000",
  "dataType": "transactions|positions",
  "assetType": "equity",
  "start": "YYYY-MM-DD",
  "end": "YYYY-MM-DD",
  "force": false,
  "dryRun": false
}
```
**Comportamento:**
1. Validar `X-Tenant-Id`, `cpf` (11), `dataType`, `assetType`, `start`, `end`.
2. Selecionar **RAW** de `b3_raw_data_client` que intersecta o período e **ainda não está normalizado** (segundo marcações internas) — ou todos se `force=true`.
3. Para cada RAW, iterar itens do JSON (mantendo `sequence_in_raw`), gerar registros normalizados com **hash** determinístico e **upsert idempotente**.
4. Atualizar marcações no RAW (ex.: `normalized_at`, `normalized_count`).
5. Retornar **sumário**: `{inserted, updated, skipped, errors, rawProcessed}`.

**Flags:**
- `force=true` → reprocessa RAW e regrava (idempotente por `normalized_hash`).
- `dryRun=true` → simula normalização, retorna **plano** (quantos registros seriam inseridos/atualizados) sem gravar.

## 🔁 Concorrência & Resiliência
- Lock por `(tenantId, cpf, dataType)` durante execução para evitar corrida.
- Operações de banco em **batch** quando possível; transações para consistência por RAW.
- Tratar erros de schema/parse e registrar no `extra_json` + log.
- Retentar RAW com falha **N** vezes e emitir alerta se exceder (usar política do 1.6/1.9).
