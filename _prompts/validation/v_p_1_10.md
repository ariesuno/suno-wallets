# Prompt de Validação 1.10v — Normalization Layer (B3 RAW → Normalized) — **suno-wallets**

## 🎯 Objetivo
Validar se a implementação do **Prompt 1.10** está 100% conforme as diretrizes: DDD, idempotência, **linhagem** (FK para RAW), schema de tabelas normalizadas, segurança/observabilidade, documentação e testes.

---

## ✅ Checklist de Validação

### 1) Arquitetura & DDD
- [ ] Artefatos criados conforme especificação:
  - `src/Application/B3/normalize/normalize_service.go`
  - `src/Infrastructure/B3/normalize/transactions_parser.go`
  - `src/Infrastructure/B3/normalize/positions_parser.go`
  - `src/Infrastructure/B3/normalize/normalized_repository.go`
  - `src/Api/Controllers/B3/normalize_controller.go` (`POST /b3/normalize/run`)
  - `src/Shared/Hash/normalized_hash.go`
- [ ] Uso de **interfaces** do domínio quando aplicável; `Application` não depende de implementações concretas.
- [ ] Nomes em **inglês**; comentários em **pt-BR**; arquivos coesos (≤ ~300 linhas).
- [ ] Validações comuns (CPF/datas) **reutilizadas** de `src/Shared/Validation/b3_input_validation.go`.

### 2) Migrations & Schema (PostgreSQL)
- [ ] **`b3_normalized_transactions`** criada com campos e tipos previstos (ajustados ao payload v2), incluindo:
  - `raw_id` (FK para `b3_raw_data_client(id)`), `sequence_in_raw` (ordem no JSON)
  - `tenant_id`, `cpf` (11), `asset_type`, `source_version`
  - datas, `ticker` (UPPER), `side` (`BUY`/`SELL`/`OTHER`), `quantity/price` como `numeric(28,10)`
  - `extra_json` (jsonb) para sobras
  - `normalized_hash` (SHA-256 determinístico)
  - **UNIQUE** composta conforme proposta (incl. `normalized_hash` + chaves)
- [ ] **`b3_normalized_positions`** criada com campos e tipos previstos (ajustados ao payload v3), incluindo:
  - `raw_id` (FK), `sequence_in_raw`
  - `reference_date` (DATE), `ticker` (UPPER), `quantity` `numeric(28,10)`
  - `avg_price` e `position_value` **somente se vier no payload** (sem cálculos)
  - `extra_json`, `normalized_hash`
  - **UNIQUE** composta conforme proposta
- [ ] Índices úteis criados (por `tenant_id, cpf, date/ticker`) e migrations versionadas.

### 3) Regras de Normalização
- [ ] **Sem regras de negócio** (NÃO calcular PM, P&L, impostos, etc.).
- [ ] Datas convertidas para **DATE** quando apropriado.
- [ ] `ticker` convertido para **upper-case**; `cpf` apenas dígitos (11).
- [ ] `side` mapeado para `BUY`/`SELL`/`OTHER`; valores desconhecidos → `OTHER` + registro em `extra_json`.
- [ ] Campos ausentes **não** recebem valores inventados; manter `NULL` ou ir para `extra_json`.

### 4) Idempotência & Linhagem
- [ ] `normalized_hash` **canônico** calculado a partir de **campos-chave**.
- [ ] **Upsert idempotente** (não duplica registros já normalizados).
- [ ] `raw_id` + `sequence_in_raw` mantêm **linhagem** com a origem RAW.
- [ ] Flags **`force`** (reprocessa mantendo idempotência) e **`dryRun`** (simula, sem persistir) funcionando.

### 5) Fluxo & Endpoint
- [ ] `POST /b3/normalize/run` recebe: `cpf`, `dataType`, `assetType`, `start`, `end`, `force`, `dryRun`.
- [ ] Seleção de RAW **pendente** no intervalo (ou tudo com `force=true`).
- [ ] Ao final, retorna **sumário** com `{inserted, updated, skipped, errors, rawProcessed}`.
- [ ] Sem gravação quando `dryRun=true`.

### 6) Concorrência & Resiliência
- [ ] Lock por `(tenantId, cpf, dataType)` durante execução.
- [ ] Operações em **batch** quando possível; transação por RAW para consistência.
- [ ] Tratamento robusto de erros de parse/schema com log + anotação em `extra_json`.

### 7) Observabilidade & Segurança
- [ ] Logs estruturados (JSON) com `tenantId`, `cpfMasked`, `dataType`, `assetType`, `rawId`, `items`, `inserted`, `updated`, `skipped`, `errors`, `durationMs`.
- [ ] Métricas Prometheus: `b3_normalize_inserted_total`, `..._updated_total`, `..._skipped_total`, `..._errors_total`; histogram de duração.
- [ ] **Nunca** logar tokens/segredos; **mascarar CPF**; variáveis sensíveis via env.
- [ ] Auditoria: registra **quem** acionou, quando e escopo processado.

### 8) Documentação
- [ ] **Swagger** (tag `B3 Data (Normalization)`), incluindo códigos de erro.
- [ ] **Postman/Bruno** atualizados com requisições reais (sanitizadas).
- [ ] `docs/b3/normalization.md` criado/atualizado (exemplos de entrada/saída, schema, decisões de tipagem).

### 9) Testes
- **Unit** (`src/Tests/Unit/B3/normalize/...`):
  - [ ] Parsers para v2/v3: datas, side, ticker uppercase, `numeric(28,10)`, `extra_json`.
  - [ ] Idempotência via `normalized_hash` (rodar 2x e verificar não duplicação).
  - [ ] `force` e `dryRun`.
- **Integration** (`src/Tests/Integration/B3/normalize/...`):
  - [ ] Execução sobre RAW existente; verificação de FKs, índices, contagens e sumário.
  - [ ] Sem dados fake sem autorização; pausar e solicitar instruções se faltar dado real.

## 📌 Resultado Esperado
Ao executar `POST /b3/normalize/run` com entradas válidas:
1. Apenas RAW pendente é processado (ou tudo se `force=true`).
2. Registros normalizados são **upsertados** (sem duplicidade).
3. `raw_id`/`sequence_in_raw` garantem **linhagem**.
4. `dryRun=true` **não persiste**; apenas retorna o plano.
5. Logs/métricas/auditoria registram o processamento.

```
Validação concluída: Etapa 1.10 (Normalization Layer) está 100% conforme.
```
