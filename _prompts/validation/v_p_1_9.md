# Prompt de Validação 1.9v — B3 RAW Persistence (historical ingest)

## 🎯 Objetivo
Validar se a implementação do **Prompt 1.9 — B3 RAW Persistence** está 100% conforme as diretrizes do projeto **suno-wallets** e o contrato oficial da B3 (v2/v3), garantindo idempotência, cobertura por período, segurança, observabilidade e documentação.

---

## ✅ Checklist de Validação

### 1) Arquitetura & DDD
- [ ] Artefatos criados conforme especificação:
  - `src/Infrastructure/B3/persistence/raw_repository.go`
  - `src/Infrastructure/B3/persistence/fetched_periods_repository.go`
  - `src/Application/B3/ingest/ingest_service.go`
  - `src/Api/Controllers/B3/ingest_controller.go` (POST `/b3/fetch/historical`)
  - `src/Shared/Hash/payload_hash.go`
  - `src/Shared/Validation/b3_input_validation.go` (reuso)
- [ ] **Uso obrigatório** do `B3OfficialClient.makeRequest(...)` (mTLS, OAuth2, retry, timeout, logs, métricas).
- [ ] **Nomes em inglês**, **comentários em pt-BR**, arquivos coesos (≤ ~300 linhas).
- [ ] Camadas respeitadas (Domain não conhece Infra; Application orquestra; Api valida e chama Application).

### 2) Migrations & Esquema de Banco
- [ ] Tabela `b3_raw_data_client` criada com campos e índices:
  - Chave de unicidade: (`tenant_id`,`cpf`,`data_type`,`asset_type`,`period_start`,`period_end`,`page`,`payload_hash`).
  - `payload_json` (JSONB), `payload_hash` (SHA-256 de payload + chaves), `endpoint_path`, `http_status`, `retry_count`, `request_id`, `source_version`.
- [ ] Tabela `b3_fetched_periods` criada com:
  - **UNIQUE** (`tenant_id`,`cpf`,`data_type`,`asset_type`,`month_start`), `pages`, `completed`, `last_fetched_at`.
- [ ] Migrations versionadas e executáveis via Docker/CLI.

### 3) Validações de Entrada (Controller)
- [ ] Header `X-Tenant-Id` obrigatório.
- [ ] Body com `cpf` (11 dígitos), `dataType` (`transactions|positions`), `assetType` (ex. `equity`), `start`, `end` (`YYYY-MM-DD`), `fetchAllPages`, `force`, `dryRun`.
- [ ] Retorna **400** com mensagem clara para parâmetros inválidos.

### 4) Lógica de Ingestão & Cobertura
- [ ] Janela **mensal** construída entre `start` e `end`.
- [ ] Antes de chamar a B3, checa `b3_fetched_periods`:
  - Se **completo** e `force=false` → **pula** o mês.
  - Se **incompleto** ou `force=true` → busca páginas faltantes.
- [ ] Para cada página:
  - Calcula `payload_hash` **canônico** (payload normalizado + chaves de contexto).
  - **Upsert idempotente** em `b3_raw_data_client` (não duplica).
  - Atualiza `pages` e marca `completed=true` quando terminar o mês.
- [ ] Suporta `dryRun=true` (não grava; retorna apenas o plano).

### 5) Concurrency & Resiliência
- [ ] Lock por `(tenantId, cpf)` durante ingestão histórica (Redis lock ou advisory lock no DB).
- [ ] Retries com **backoff + jitter** para `429/5xx` (política do 1.6).
- [ ] Timeout por requisição; `context.Context` utilizado adequadamente.
- [ ] Tratamento de `401/403` com instrução de renovar credenciais.

### 6) Observabilidade & Auditoria
- [ ] Logs estruturados (JSON) com: `tenantId`, `cpfMasked`, `dataType`, `assetType`, `monthStart`, `page`, `httpStatus`, `durationMs`, `saved`, `skipped`, `retries`.
- [ ] Métricas Prometheus expostas/incrementadas:
  - `b3_raw_saved_total`, `b3_raw_skipped_total`, `b3_raw_errors_total`.
  - `b3_raw_pages_processed_total`, `b3_raw_months_completed_total`.
  - Histograma de duração por página/mês.
- [ ] Auditoria registra **quem** executou (ex.: `userId`), data/hora e escopo do ingest.

### 7) Segurança & Governança
- [ ] **RAW nunca excluído automaticamente** (purge somente manual via comando explícito e log de auditoria).
- [ ] **CPF mascarado** em logs; tokens/segredos **nunca** logados.
- [ ] Variáveis sensíveis via **env** (sem hardcode).

### 8) Endpoint & Resposta
- [ ] `POST /b3/fetch/historical` implementado conforme contrato.
- [ ] Retorna **sumário**:
  ```json
  {
    "saved": <int>,
    "skipped": <int>,
    "errors": <int>,
    "monthsProcessed": <int>,
    "pagesProcessed": <int>,
    "dryRun": <bool>,
    "force": <bool>
  }
  ```
- [ ] Respostas de erro padronizadas (400/401/403/429/5xx).

### 9) Documentação
- [ ] **Swagger** (tag `B3 Data (Persistence)`) com request/response e códigos de erro.
- [ ] **Postman/Bruno** atualizados com chamada real (sanitizada).
- [ ] `docs/b3/raw_persistence.md` com: janelas mensais, deduplicação, índices, cURL.

### 10) Testes
- **Unit** (`src/Tests/Unit/B3/ingest/...`):
  - [ ] Geração de janelas mensais, skip por completude, flags `force`/`dryRun`.
  - [ ] Cálculo de `payload_hash` e idempotência.
  - [ ] Erros 400/401/403/429/5xx (simulados).
- **Integration** (`src/Tests/Integration/B3/ingest/...`):
  - [ ] Smoke do endpoint com env real (se disponível).
  - [ ] **Sem dados fake** sem autorização explícita; pausar e solicitar instruções se faltar dado real.

---

## 📌 Resultado Esperado
Ao executar `POST /b3/fetch/historical` com `cpf`, `dataType`, `assetType`, `start` e `end` válidos:
1. O serviço avalia cobertura mensal existente e **busca apenas o que falta** (ou tudo se `force=true`).
2. Páginas são processadas com retry/backoff quando necessário.
3. **RAW é persistido** com `upsert` idempotente e `payload_hash` canônico.
4. `b3_fetched_periods` é atualizado com `pages` e `completed`.
5. O sumário é retornado com `{saved, skipped, errors, monthsProcessed, pagesProcessed, ...}`.
6. Logs e métricas são registrados (sem vazar PII/segredos).

Se **tudo** estiver conforme, responda:
```
Validação concluída: Etapa 1.9 (B3 RAW Persistence) está 100% conforme.
```

Caso contrário, liste **exatamente** os itens pendentes/corretivos e como endereçá-los.
